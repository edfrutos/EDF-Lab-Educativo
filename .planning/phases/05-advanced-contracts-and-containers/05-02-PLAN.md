**Crear api/Dockerfile con exactamente este contenido:**

```dockerfile
FROM node:22-alpine

# Directorio de trabajo dentro del contenedor
WORKDIR /usr/src/app

# Copiar manifiestos primero — aprovecha caché de capas Docker
COPY package*.json ./

# Instalar solo dependencias de producción
RUN npm ci --omit=dev

# Copiar el resto del código fuente
COPY . .

# Exponer el puerto que usa la API
EXPOSE 3100

# Variable de entorno: index.js usa `process.env.PORT || 3000` por defecto.
# Sin esta línea el contenedor escucharía en 3000 aunque el script publique -p 3100:3100.
ENV PORT=3100

# Usuario no-root — la imagen node:22-alpine incluye el usuario 'node'.
# DEBE ir después de todos los COPY para evitar problemas de permisos de lectura.
USER node

# CMD directo a node (no npm start): los signals SIGTERM llegan al proceso Node.js,
# no al proceso npm intermedio.
CMD ["node", "index.js"]
```

**Crear api/.dockerignore con exactamente este contenido:**

```
node_modules
.git
*.test.js
data/users.json
```

Razón de cada exclusión:
- `node_modules`: se reconstruyen con `npm ci` dentro del contenedor. Incluirlos haría la imagen ~3x más grande y potencialmente incompatible (binarios compilados para el host vs Alpine).
- `.git`: metadatos de control de versiones, innecesarios en la imagen.
- `*.test.js`: el fichero `index.test.js` y sus fixtures no deben ir a producción/contenedor.
- `data/users.json`: si se incluye, el contenedor hereda el estado del host. Excluirlo hace que el contenedor arranque desde `SEED_DATA` (comportamiento efímero correcto).

**Actualizar api/package.json — añadir dos scripts manteniendo la alineación de espacios:**

El bloque `scripts` completo debe quedar así (alineación con espacios como el resto):
```json
"scripts": {
  "start":        "node index.js",
  "dev":          "nodemon index.js",
  "test":         "node --test index.test.js --test-force-exit",
  "docker:build": "docker build -t edf-lab-api .",
  "docker:start": "docker run --rm -p 3100:3100 --name edf-lab-api edf-lab-api"
},
```

Explicación de los flags del script `docker:start`:
- `--rm`: elimina el contenedor al pararlo (comportamiento efímero, no acumula contenedores parados)
- `-p 3100:3100`: publica el puerto 3100 del contenedor en el puerto 3100 del host
- `--name edf-lab-api`: nombre legible para usar en `docker logs edf-lab-api` y `docker stop edf-lab-api`
- `edf-lab-api` final: nombre de la imagen a usar (el mismo que en `docker:build -t edf-lab-api`)

IMPORTANTE: No añadir `docker:stop` como script — `docker stop edf-lab-api` es trivial y se documenta en docs/12-docker.md sin necesitar un alias npm.

```
# Docker: arrancar la API en un contenedor

¿Ya sabes arrancar la API con `npm start`? Bien. Este documento te enseña otra forma — con Docker. La primera forma sigue funcionando igual.

---

## ¿Qué es un contenedor?

[Explicar: un contenedor es un proceso aislado con su propio sistema de ficheros, red y variables de entorno. No es una máquina virtual — comparte el kernel del sistema operativo del host pero está aislado de él. Analogía: como un proceso en una caja sellada.]

---

## ¿Qué es una imagen?

[Explicar: una imagen es la plantilla a partir de la cual se crean los contenedores. Es inmutable — siempre produce el mismo contenedor. La imagen se construye una vez; los contenedores se crean y destruyen tantas veces como sea necesario.]

### La diferencia clave

| Concepto | Analogía | En este lab |
|----------|----------|-------------|
| Imagen | Molde de galletas | `edf-lab-api` (construida con `npm run docker:build`) |
| Contenedor | Galleta | El proceso que arranca con `npm run docker:start` |
| `docker build` | Crear el molde | Instala deps, copia código |
| `docker run` | Usar el molde | Arranca `node index.js` |

---

## El flujo completo: build → run → logs → stop

[Diagrama ASCII del port mapping:]

[Tu Mac - Puerto 3100]
        |
        |  -p 3100:3100
        |
[Contenedor Docker]
        |
   api/index.js
   (Node.js 22)
        |
   datos efímeros
   (SEED_DATA)

[Explicar que -p 3100:3100 mapea el puerto 3100 del host al puerto 3100 del contenedor. Sin ese flag, el contenedor escucha internamente pero no es accesible desde el host.]

### Comandos paso a paso

```bash
# 1. Construir la imagen (solo la primera vez o tras cambios en el código)
cd api
npm run docker:build
# → docker build -t edf-lab-api .

# 2. Arrancar el contenedor
npm run docker:start
# → docker run --rm -p 3100:3100 --name edf-lab-api edf-lab-api

# 3. Verificar que la API responde (en otra terminal)
curl http://localhost:3100/health

# 4. Ver los logs del contenedor
docker logs edf-lab-api

# 5. Parar el contenedor
docker stop edf-lab-api
# El flag --rm hace que el contenedor se elimine automáticamente al parar
```

---

## Datos efímeros: el contenedor arranca limpio

[Explicar: data/users.json NO se copia dentro de la imagen (está en .dockerignore). Cada vez que arrancas el contenedor, la API empieza con los dos usuarios del SEED_DATA. Cuando paras el contenedor, los usuarios creados dentro se pierden. Esto no es un error — es el comportamiento correcto de un contenedor sin volúmenes montados.]

| Arranque | ¿Persisten los datos? |
|----------|----------------------|
| `npm start` en el host | Sí — `data/users.json` mantiene los cambios |
| `npm run docker:start` | No — el contenedor arranca desde SEED_DATA cada vez |

[Nota: Docker ofrece volúmenes para persistencia en contenedores, pero eso es material para una fase avanzada. Por ahora, la efimeridad es la lección correcta.]

---

## Resumen

[2-3 frases: Docker permite arrancar la API en un entorno aislado y reproducible. El mismo `index.js` funciona en el contenedor sin ningún cambio. Para practicar el flujo completo, ve a la Misión 09.]

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| host filesystem → contenedor | COPY en Dockerfile — determina qué ficheros entran en la imagen |
| contenedor → host network | -p 3100:3100 mapea puertos del contenedor al host |
| host → Docker daemon | npm run docker:build/start invoca Docker con privilegios de daemon |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-02-01 | Information Disclosure | api/.dockerignore | mitigate | data/users.json excluido del contexto de build — datos de usuarios del host no entran en la imagen. node_modules excluidos — ningún artefacto de desarrollo en la imagen. |
| T-05-02-02 | Elevation of Privilege | api/Dockerfile (USER node) | mitigate | `USER node` antes de `CMD` — el proceso Node.js corre como usuario no-root dentro del contenedor. Sigue las buenas prácticas de nodejs/docker-node. |
| T-05-02-03 | Denial of Service | docker run --name edf-lab-api | accept | El nombre fijo puede causar conflicto si ya hay un contenedor con ese nombre. En contexto educativo local con un solo alumno, riesgo mínimo. El flag --rm limpia el contenedor al parar. |
| T-05-02-04 | Tampering | CMD ["node", "index.js"] vs CMD ["npm", "start"] | mitigate | CMD directo a node garantiza que SIGTERM llega al proceso Node.js. Con npm start, npm intercepta la señal y el proceso puede quedar zombie. Documentado en Dockerfile con comentario. |
| T-05-02-05 | Information Disclosure | ENV PORT=3100 en Dockerfile | accept | La variable de entorno es pública en la imagen (docker inspect). En contexto educativo, esta transparencia es un activo — el alumno puede inspeccionarla. No contiene secretos. |
</threat_model>
